SPARK · REGRESSION ASSAY/2026-08-22

Did the resident brain make SPARK worse?

Master (05629e79) vs. the pre-resident cold-start bridge (3084368b), measured three ways: cognition in isolation, a from-scratch minimal resident harness, and live behaviour on the actual robot.

01 — Verdict
Recommendation: Retain current architecture, fix one narrow regression

On identical prompts, the resident brain answered faster (18.8s vs 30.2s median) and more correctly (it recalled a fact it was told 90 seconds earlier; the cold-start bridge confidently denied ever being told). The resident architecture isn't the liability — a naive resident session is: a from-scratch minimal harness with zero SPARK-specific engineering never once delivered a reply through its own designated channel, in 14 for 14 turns. Production's hardening is what separates a working resident brain from a non-functional one.

The one clear, narrow regression: when the resident brain does time out, current master can now fail silently (a new wake-grant gate suppresses even the fallback acknowledgment without a live wake event), where the old build always spoke something. That's fixable without touching the architecture — see §06.

03 — Layer C · Minimal resident, built from scratch

Is "resident" the problem, or is it SPARK's specific implementation?

A dedicated tmux session, empty cwd, no project CLAUDE.md, the same conversational system prompt as Layer A plus one instruction ("reply by running this script"), one tool in its allowlist, direct request→response — the smallest resident Claude Code harness that could answer the same 14 prompts.

This is the exact failure mode that caused the real 4h43m production outage (#226): the model narrates a well-formed answer instead of executing the tool that delivers it. It happened on every single turn, with zero SPARK complexity in the way — no reflection, no vision, no multi-kind routing, no large system prompt. The content was usually good (it correctly asked for wheels-on-blocks confirmation before a drive request it was never told was safe), but none of it ever reached a caller.

Read against Layer A, where the production spark-brain setup delivered 13/14 through its tool: the gap between 0% and 93% is entirely the hardening already sitting on top of the base architecture — the exact reply-tool wording, the absolute-path rule, the "reply exactly once" instruction, the mailbox protocol. That hardening is the product of fixing #226 the first time. Reverting the architecture would not remove this failure mode; it would remove the fix for it.

04 — Layer B · The actual robot, today

When you say "Hey Spark," what happens before cognition even starts

A genuine wake-word detection at 15:23:18 — vosk heard "hey spark" correctly. What followed was upstream of everything measured in §02–03:

The resident-vs-cold-start question was never engaged: run_conversation() returns immediately on an empty transcript, before either backend would be called. This is a real, live defect in the wake/STT capture stage — but that stage is byte-identical between 3084368b and HEAD (confirmed in the 116-file diff), so it is not attributable to the resident-brain migration. It would very likely reproduce the same way on the old build.

A second real attempt, minutes later, worked end to end. Wake detected at 15:34:15, this time recording started immediately (no repeat of the 14s gap), captured a real utterance, and ran two full conversation turns through the actual production stack — wake → STT → spark-brain (kind voice_turn) → policy → spoken reply — both completing with voice loop rc=0. The three underlying brain replies logged during it took 10.5s, 14.3s and 9.3s: well inside budget, consistent with Layer A's median. So the empty-transcript failure in the first attempt was a real but intermittent fault, not a standing block — current master can and does complete a genuine "Hey Spark" round trip today.

05 — Observations vs. causal inference

Observed (facts)

  • Resident brain: 13/14 success, median 18.8s, one 86.5s outlier that broke its own declared 45s budget.
  • Cold bridge: 13/14 success, median 30.2s, one 120.1s hang against no declared budget at all.
  • Cold bridge fabricated a false "I don't know that" twice on a fact it had correctly stored moments earlier.
  • A from-scratch minimal resident harness delivered 0/14 replies through its designated channel, always narrating in the pane instead.
  • A real wake event today produced an empty transcript before cognition was ever reached; wake/STT code is unchanged since 3084368b.
  • A second real wake event minutes later completed two full turns end to end (rc=0 both times), with brain replies at 10.5s / 14.3s / 9.3s — comfortably on budget.
  • 11 voice_turn brain-timeout/unavailable events logged in production today before this test began; 517 since 2026-08-17.
  • 20-minute idle soak on master: load falling, memory/swap flat, all services active, brain marker stayed validated throughout.

Causal candidates (not proven)

  • The resident brain's tail latency (the 86.5s call) may be queueing/contention on the single-flight session lock shared with reflection and other kinds — not measured directly here.
  • The cold bridge's memory fabrication is plausibly a generic cold-model tendency to answer conversationally rather than invoke a lookup tool when no execution history is visible to it — the same broad tendency as Layer C's narration failure, in a different direction.
  • The wake/STT capture gap (enable_speaker timeout + ~14s delay) may be resource contention from the concurrent testing load this session was already generating — not isolated as the sole cause.
  • The new wake_grant gate turning a slow-brain failure into total silence is a design choice, not a bug — but it changes the old build's "always says something, eventually" property into "sometimes says nothing at all."

07 — Smallest experiment that could falsify this recommendation
Next step

Instrument the real base rate and root cause of the voice_turn tail-latency failures (§06) across a week of actual family use — not synthetic back-to-back calls, which may themselves induce contention this assay can't distinguish from a structural issue. Specifically: does elapsed time correlate with concurrent reflection/other-kind traffic on the same single-flight lock, or with session context size approaching a recycle boundary?

This recommendation is wrong if

the real-world base rate turns out far higher than the ~1-in-14 sampled here — e.g. north of 10-20% under actual family conversational timing. At that rate, "resident is faster and more correct on average" is swamped by "resident goes silent on a meaningful fraction of real summons," and the recommendation flips toward narrowly reverting or bypassing the resident path specifically for the voice_turn kind — not the architecture as a whole.

Smallest safe fix for the one confirmed narrow regression (§01): let acknowledge_unavailable()'s single deterministic line bypass the wake-grant check specifically — it is not model output, carries no content risk, and its entire purpose is telling a person who just summoned SPARK that they were heard. Everything else about the wake-grant gate stays exactly as designed.

Methodology note: no git checkout or service swap to 3084368b was performed. The old build's cognition layer was measured by extracting bin/claude-voice-bridge and calling it directly with an identical prompt — its full historical wake/systemd/resource stack was not reconstructed and is out of scope for this assay. Production was never mutated; all comparisons ran against extracted or from-scratch harnesses alongside the live system.
