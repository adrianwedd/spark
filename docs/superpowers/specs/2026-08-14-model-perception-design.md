# Model-Mediated Perception Provenance — Design Spec

**Date:** 2026-08-14
**Issue:** #177
**Scope:** `src/pxh/provenance.py`, `bin/px-wander`, `bin/tool-recall`, provenance and exploration tests, operator/developer documentation

## Problem

SPARK's durable provenance currently calls `observation` something he "saw himself" and permits confidence up to `1.0`. That is appropriate for direct sensor values and deterministic transforms, but not for prose generated by a vision model from a camera frame. The frame is sensor evidence; the description is an interpretation of that evidence and can hallucinate, omit, or misidentify details.

Treating both as `observation` collapses an epistemically meaningful boundary. Treating model interpretation as ordinary `inference` also loses information: unlike an unsupported inference, it is grounded in a particular sensor input or perception event.

The ontology therefore needs one general kind for model-mediated interpretation of sensor evidence. It must change downstream language and confidence, not merely add taxonomy.

## Decision

Add `model_perception` for claims produced by a model interpreting sensor evidence.

The kind is modality-independent. Claude vision interpreting a JPEG is the first writer, but the same kind can later describe a model interpreting microphone, depth, thermal, or other sensor input. Modality belongs in `source` and `evidence`, not in the kind name.

Reserve `observation` for:

- direct sensor values;
- deterministic transforms of sensor values; and
- claims whose semantic content does not depend on a generative or learned interpretation step.

`exploration.jsonl` may continue using `type: "observation"`. That field classifies an exploration event; it does not grant durable epistemic authority. Durable notes and memories obtain authority only from their `provenance` block.

## Confidence Ordering

The safety ordering is:

```text
observation / verification  1.00
report                      0.90
model_perception            0.75
inference                   0.60
narrative                   0.50
unknown                     0.30
```

`model_perception` defaults to `0.65` and is capped at `0.75` on both write and read.

This position is deliberate:

- below a human/external report, because the model can generate unsupported visual detail;
- above unsupported inference, because the claim is grounded in a concrete sensor event;
- above narrative, because it is constrained by external input rather than generated only from SPARK's inner prose.

These constants remain outside `spark_config.py`, preserving the rule that self-evolution cannot raise epistemic ceilings.

## Evidence Invariant

Every `model_perception` record must retain at least one non-empty evidence reference sufficient to identify the sensor artifact or perception event that grounded the interpretation.

A valid reference may identify:

- a retained sensor artifact, such as an image identifier or durable path;
- a durable sensor/perception event, such as an exploration observation ID; or
- an external event identifier, such as a Frigate event ID.

A source label alone is not evidence. `source: "claude_vision"` says who interpreted the input but not which input grounded the claim.

The first writer will use a stable exploration observation reference:

```text
exploration:<explore_id>:observation:<observation_id>
```

The referenced `exploration.jsonl` event contains the timestamp, exploration ID, step, heading, sonar value, Frigate labels, model description, and vision-success flag. Raw camera images need not be retained solely for provenance; retaining every household image would create a disproportionate privacy and storage cost. The durable event is the grounding record.

The write ordering is mandatory:

1. capture the sensor input successfully;
2. obtain a non-fallback model interpretation;
3. create a stable observation event ID;
4. persist the exploration observation event successfully;
5. only then persist an interesting durable note as `model_perception`, referencing that event.

If capture, interpretation, event persistence, or evidence construction fails, no `model_perception` record is written. A failed description may remain in operational logs as a failure, but it cannot become durable epistemic content.

The provenance API enforces this invariant centrally: `make_provenance()` rejects `model_perception` without evidence. `read_provenance()` remains lenient and degrades a stored `model_perception` with missing/invalid evidence to `unknown`; malformed disk state must never gain authority or crash a reader.

## Current Writer Inventory

### Model-derived durable perception

`bin/px-wander` is the only current path that turns model-derived sensor interpretation into a durable claim:

1. `_call_describe_scene()` invokes `tool-describe-scene`;
2. `tool-describe-scene` asks Claude vision to interpret a camera frame;
3. successful interesting descriptions call `_auto_remember()`;
4. `_auto_remember()` currently writes an untyped note with `source: "exploration"`.

The existing provenance module documentation describes wander scene descriptions as `observation`, but the extracted current writer does not actually stamp that kind. Untyped notes therefore read as legacy/`unknown`. The implementation will correct the forward writer without retroactively inferring provenance from `source`.

### Related paths that are not durable provenance writers

- `tool-describe-scene` returns and logs a description but does not write notes or memories.
- `exploration.jsonl` records navigation and perception events; `type: "observation"` is an event type, not a provenance kind.
- `src/pxh/mind.py` and `src/pxh/voice_loop.py` read recent exploration events into cognition or conversation but do not promote them into durable provenance records.
- `bin/tool-recall` renders stored provenance but does not create it.
- Frigate labels are also learned-model outputs. Any future durable claim derived from those labels must use `model_perception`, not `observation`.

No current production writer correctly stamps a model-derived durable claim as explicit `observation`; the overstatement currently exists in the ontology documentation, intended writer semantics, and recall behavior that would apply if such a record were written.

## Writer Design

`bin/px-wander` will use the shared provenance module rather than hand-building metadata.

Each successful vision observation receives a stable `observation_id`. `_write_observation()` returns success/failure so promotion cannot race ahead of evidence persistence. For an interesting, successfully persisted observation, `_auto_remember()` writes a record equivalent to:

```json
{
  "id": "<stable durable-note id>",
  "ts": "<UTC timestamp>",
  "note": "While exploring (...): ...",
  "source": "exploration",
  "provenance": {
    "kind": "model_perception",
    "source": "claude_vision:exploration",
    "evidence": ["exploration:<explore_id>:observation:<observation_id>"],
    "confidence": 0.65,
    "recorded_at": "<UTC timestamp>",
    "supersedes": [],
    "legacy": false
  }
}
```

The caller supplies the kind, source, and evidence as system constants/constructed identifiers. Model output cannot choose its own kind, confidence ceiling, or evidence reference.

## Downstream Behavior

The reflection/memory provenance label becomes:

```text
a model interpreted this from my sensors
```

Recall uses language that preserves the interpretation step:

- single record: `I remember my vision system interpreting: ...`
- mixed-record item: `my vision system interpreted: ...`

The first writer is vision-specific, so recall may say "vision system." The ontology label remains modality-independent. If another model-mediated modality is added, recall can later derive modality wording from the trusted `source`; until then, unknown sources should use the generic phrase "my perception system interpreted."

Retrieval ranking continues to use stored confidence. No separate ranking rule is required: the `0.75` ceiling and `0.65` default create the intended distance from direct observations.

## Migration and Compatibility

There is no bulk migration and no provenance inference from historical strings.

- Existing explicit `observation` records remain `observation`.
- Existing untyped exploration notes remain legacy/`unknown`.
- Existing legacy records remain capped by `unknown`.
- Existing `exploration.jsonl` entries remain readable without an `observation_id`.
- Only newly written model-interpreted durable claims use `model_perception`.
- A future correction may supersede an older claim, but migration never silently rewrites or promotes it.

Adding a kind is backward-compatible for lenient readers in this repository after they are updated together. An older checkout that encounters the new kind already degrades an unrecognized value to `unknown`, which is safe.

## Error Handling

- `make_provenance("model_perception", ..., evidence=[])` raises `ValueError`, because production writers passing literals have violated the contract.
- `read_provenance()` never raises. Missing/invalid evidence on stored `model_perception` degrades the block to `unknown` and applies the `unknown` ceiling.
- `_write_observation()` reports whether the evidence event was durably appended.
- `_auto_remember()` refuses model-perception persistence without a valid event reference.
- Vision fallback descriptions and `vision_failed` events are never promoted.
- Failure to persist the evidence event prevents note promotion but does not stop safe exploration.

## Test Design

### Ontology tests

- `model_perception` is an accepted kind.
- Its default confidence is `0.65` and its ceiling is `0.75` on write and read.
- The complete ceiling ordering matches the approved invariant.
- Strict writes reject missing/empty evidence.
- Lenient reads degrade malformed or evidence-free stored model perceptions to `unknown`.
- Existing explicit observations and legacy records retain their current kinds.

### Writer tests

- A successful interesting vision event is persisted before its durable note.
- The note is stamped `model_perception` with the expected stable evidence reference.
- The model description cannot supply or override kind, confidence, or evidence.
- Failed vision, failed event persistence, or missing evidence produces no durable model-perception note.
- Existing exploration entries without IDs remain readable.

### Recall tests

- Single and mixed recall use interpretation language rather than "I saw."
- Existing observation/report/inference/narrative/verification/unknown wording is unchanged.

### Verification scope

- focused provenance, memory, recall/tool, exploration, mind, and voice-loop suites;
- repository-wide suite under `PX_BYPASS_SUDO=1 LOG_DIR=logs_test`;
- verifier outcomes recorded distinctly as pass, assertion failure, timeout, or environment/setup failure, preserving #178's semantics.

## Non-Goals

- retaining every raw household image;
- retroactively reclassifying stored records;
- changing `exploration.jsonl`'s event-type vocabulary;
- letting a model select its own provenance;
- adding modality-specific provenance kinds;
- implementing belief fusion, automatic verification, or correction policies;
- changing #172's ontogeny behavior in this issue.

## Acceptance Mapping

- Raw sensor evidence versus model interpretation is explicitly distinguished.
- All current model-vision writer and reader paths are inventoried.
- `model_perception` earns a distinct confidence ceiling and recall behavior.
- Grounding evidence is mandatory and identifiable before persistence.
- Tests cover ordering, ceiling, evidence enforcement, writer behavior, recall wording, and migration invariants.
- No existing durable record is silently promoted or retyped.
